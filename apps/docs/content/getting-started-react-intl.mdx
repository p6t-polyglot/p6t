# Getting Started with react-intl

This guide sets up `react-intl` in a **Next.js App Router** project from scratch. Every decision has been made for you — follow the steps in order and you will end up with a production-ready i18n foundation.

**What you'll get:**

- Automatic message ID generation via the Next.js SWC plugin (no manual IDs, no collision risk)
- URL-segment locale routing (`/en/`, `/fr/`, …) with `Accept-Language` detection for new visitors
- Separate, correct render paths for Server Components and Client Components
- An extraction and compilation pipeline your IDE and CI can run

---

## 1. Install dependencies

```bash
pnpm add react-intl @formatjs/intl-localematcher negotiator
pnpm add -D @swc/plugin-formatjs @formatjs/cli @types/negotiator
```

| Package | Dev? | Purpose |
|---|---|---|
| `react-intl` | | Runtime formatting and React context |
| `@formatjs/intl-localematcher` | | Matches a visitor's `Accept-Language` header to your supported locales — runs in the proxy |
| `negotiator` | | Parses `Accept-Language` header values — runs in the proxy |
| `@swc/plugin-formatjs` | ✓ | SWC transform — auto-generates hash IDs and pre-compiles message AST at build time |
| `@formatjs/cli` | ✓ | `formatjs extract` and `formatjs compile` CLI commands |
| `@types/negotiator` | ✓ | TypeScript types for `negotiator` |

## 2. Configure the SWC plugin

Add the plugin to your Next.js config. It runs at build time to insert stable hash IDs into every `formatMessage` / `<FormattedMessage>` call and pre-compile ICU message syntax to AST, eliminating parser overhead at runtime.

**`next.config.ts`**

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    swcPlugins: [
      [
        '@swc/plugin-formatjs',
        {
          idInterpolationPattern: '[sha512:contenthash:base64:6]',
          ast: true,
        },
      ],
    ],
  },
}

export default nextConfig
```

The `idInterpolationPattern` must match the one you pass to `formatjs extract` in step 5.

## 3. Message file layout

Create an `i18n/` directory at the project root:

```
i18n/
  en.json          ← generated by `formatjs extract` (commit this)
  fr.json          ← translated source (commit this)
  de.json          ← translated source (commit this)
  compiled/
    en.json        ← generated by `formatjs compile` (commit this)
    fr.json
    de.json
```

Commit everything in `i18n/`. Compiled files are deterministic outputs — having them in version control means deployments never require a build step for translations and reviewers can diff translation changes.

## 4. Locale helpers

**`lib/i18n.ts`**

```ts
export const locales = ['en', 'fr', 'de'] as const
export type Locale = (typeof locales)[number]
export const defaultLocale: Locale = 'en'

export async function getMessages(locale: Locale) {
  return (await import(`../i18n/compiled/${locale}.json`)).default
}
```

This is the single place to change when you add a new locale.

## 5. Locale detection proxy

The proxy inspects the `Accept-Language` header for visitors without a locale prefix and redirects them to the best matching locale. For authenticated users, read the locale from their account first — see [Locale in authenticated apps](#locale-in-authenticated-apps).

**`proxy.ts`**

```ts
import { match } from '@formatjs/intl-localematcher'
import Negotiator from 'negotiator'
import { type NextRequest, NextResponse } from 'next/server'
import { defaultLocale, locales } from './lib/i18n'

function getLocale(request: NextRequest): string {
  const headers = {
    'accept-language': request.headers.get('accept-language') ?? '',
  }
  const languages = new Negotiator({ headers }).languages()
  return match(languages, locales as unknown as string[], defaultLocale)
}

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  const hasLocale = locales.some(
    locale => pathname.startsWith(`/${locale}/`) || pathname === `/${locale}`,
  )
  if (hasLocale) return

  const locale = getLocale(request)
  request.nextUrl.pathname = `/${locale}${pathname}`
  return NextResponse.redirect(request.nextUrl)
}

export const config = {
  matcher: ['/((?!_next|api|favicon.ico).*)'],
}
```

## 6. Layout — providing messages to the component tree

`IntlProvider` is a Client Component because it uses React context. Wrap it in a thin client boundary so your layout itself can stay a Server Component.

**`app/[locale]/providers.tsx`**

```tsx
'use client'

import { IntlProvider } from 'react-intl'
import type { Locale } from '@/lib/i18n'

export default function Providers({
  locale,
  messages,
  children,
}: {
  locale: Locale
  messages: Record<string, unknown>
  children: React.ReactNode
}) {
  return (
    <IntlProvider locale={locale} defaultLocale="en" messages={messages}>
      {children}
    </IntlProvider>
  )
}
```

**`app/[locale]/layout.tsx`**

```tsx
import { getMessages, locales, type Locale } from '@/lib/i18n'
import Providers from './providers'

export function generateStaticParams() {
  return locales.map(locale => ({ locale }))
}

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode
  params: Promise<{ locale: Locale }>
}) {
  const { locale } = await params
  const messages = await getMessages(locale)

  return (
    <html lang={locale}>
      <body>
        <Providers locale={locale} messages={messages}>
          {children}
        </Providers>
      </body>
    </html>
  )
}
```

`generateStaticParams` tells Next.js which locale segments to pre-render at build time.

## 7. Declaring messages

Always declare messages inline at their usage site. Always include a `description` — but write it to capture **intent**, not to paraphrase the text itself.

The `description` field exists because the word "Delete" means something very different as a button label in a destructive confirmation dialog versus a column header in a data table. The translator cannot know which without context. The developer writing the code is the only person who knows — so the intent must be captured at write-time, not retrofitted later.

A good description answers: *what is the user doing here, and what happens when they see or interact with this?*

```tsx
// ✅ Captures intent — the translator understands the stakes and the placement
intl.formatMessage({
  defaultMessage: 'Delete {name}',
  description: 'Confirmation button in the account deletion dialog. Permanently removes the account with no undo. {name} is the account username.',
}, { name })

// ✅ Intent is clear — this is a save action, in a specific form, not a generic label
<FormattedMessage
  defaultMessage="Save changes"
  description="Primary action button in the profile settings form. Commits all pending changes."
/>

// ❌ Describes the text, not the intent — gives the translator nothing useful
intl.formatMessage({
  defaultMessage: 'Delete {name}',
  description: 'A button for deleting.',
})

// ❌ No description at all
intl.formatMessage({ defaultMessage: 'Save' })

// ❌ Pre-declared with defineMessage — loses colocation benefit, avoid unless necessary
const msg = defineMessage({ defaultMessage: 'Save' })
```

The SWC plugin replaces the inline `defaultMessage` with a hash ID in the compiled output — you never write or manage IDs by hand.

## 8. Client Components

Client Components access the `IntlProvider` context via `useIntl()` or `<FormattedMessage>`:

**`app/[locale]/delete-button.tsx`**

```tsx
'use client'

import { FormattedMessage, useIntl } from 'react-intl'

export default function DeleteButton({ name }: { name: string }) {
  const intl = useIntl()

  return (
    <button
      aria-label={intl.formatMessage(
        {
          defaultMessage: 'Delete {name}',
          description: 'Accessible label on the delete button in the user list. Opens a confirmation dialog — does not immediately delete. {name} is the account username.',
        },
        { name },
      )}
    >
      <FormattedMessage
        defaultMessage="Confirm deletion"
        description="Primary action button inside the delete confirmation dialog. Clicking this permanently removes the account."
      />
    </button>
  )
}
```

## 9. Server Components

Server Components cannot use React context, so they cannot read from `IntlProvider`. Use `createIntl` from `react-intl/server` instead:

**`app/[locale]/page.tsx`**

```tsx
import { createIntl, createIntlCache } from 'react-intl/server'
import { getMessages, type Locale } from '@/lib/i18n'

// One cache instance per module, shared across requests.
// Prevents repeated construction of Intl objects.
const cache = createIntlCache()

export default async function Page({
  params,
}: {
  params: Promise<{ locale: Locale }>
}) {
  const { locale } = await params
  const messages = await getMessages(locale)
  const intl = createIntl({ locale, messages }, cache)

  return (
    <main>
      <h1>
        {intl.formatMessage({
          defaultMessage: 'Welcome back',
          description: 'H1 heading on the dashboard. Shown after a successful login — the user has just arrived at their home screen.',
        })}
      </h1>
      <p>
        {intl.formatMessage(
          {
            defaultMessage: 'Last login: {date, date, long}',
            description: 'Subtitle under the dashboard heading. Reassures the user about account security by showing when their session was last active. {date} is a JavaScript Date object.',
          },
          { date: new Date() },
        )}
      </p>
    </main>
  )
}
```

> `react-intl/server` re-exports only the non-React parts (`createIntl`, `createIntlCache`, `defineMessage`, `defineMessages`). Importing it in a Server Component does not create a client boundary.

## 10. Extract and compile

Add these scripts to `package.json`:

```json
{
  "scripts": {
    "i18n:extract": "formatjs extract 'src/**/*.{ts,tsx}' --ignore='**/*.d.ts' --out-file i18n/en.json --id-interpolation-pattern '[sha512:contenthash:base64:6]'",
    "i18n:compile": "formatjs compile-folder i18n i18n/compiled --ast"
  }
}
```

`compile-folder` compiles every `i18n/<locale>.json` to `i18n/compiled/<locale>.json` in one pass. Adding a new locale requires no script change — drop the file in `i18n/` and run the command.

**Typical workflow when adding or changing strings:**

```bash
# 1. After writing new messages in source code:
pnpm i18n:extract
# → updates i18n/en.json with new hash IDs

# 2. Translate i18n/fr.json and i18n/de.json
#    (manually, or with `p6t translate` — see below)

# 3. Compile all locales to AST:
pnpm i18n:compile

# 4. Commit everything under i18n/
git add i18n/ && git commit -m "chore: update translations"
```

The `--ast` flag compiles ICU message syntax to a parsed tree. react-intl detects pre-compiled messages automatically and skips the runtime parser, reducing bundle work and improving render performance.

## 11. Lint your messages

`eslint-plugin-formatjs` catches problems at the editor and CI level — missing descriptions, invalid ICU syntax, manual IDs, unmatched placeholders — before they reach extraction or translation.

```bash
pnpm add -D eslint-plugin-formatjs
```

Add to your ESLint flat config:

**`eslint.config.mjs`**

```js
import formatjs from 'eslint-plugin-formatjs'

export default [
  // ... your other configs

  {
    plugins: { formatjs },
    rules: {
      ...formatjs.configs.recommended.rules,

      // Require a literal description on every message — captures the intent
      // of the message (why it exists, what the user is doing) at write-time,
      // when the developer has the full context. Translators cannot infer this later.
      'formatjs/enforce-description': ['error', 'literal'],

      // Ban hand-written IDs. The SWC plugin generates them; no one should
      // be adding an `id` field by hand.
      'formatjs/no-id': 'error',
    },
  },
]
```

`recommended` covers the rest: `no-invalid-icu`, `no-offset`, `enforce-placeholders`, `prefer-full-sentence`, `no-multiple-whitespaces`, and more. The two rules added on top enforce the specific decisions made in this guide.

## Locale in authenticated apps

URL segments (`/en/`, `/fr/`) are the right default and what this guide implements. For apps with user accounts, the locale the user selected in their settings is the canonical source of truth — the `Accept-Language` fallback in the proxy is only for new visitors.

In practice this means: query the user's `locale` column from your session/database at the start of the proxy, and only fall back to the `getLocale()` header detection when no user session exists. Store and update the preference in your user profile settings whenever the user changes their language.

A dedicated guide for this pattern — including the proxy update and a locale selector component — is planned.

## Adding p6t

Once your extraction and compilation pipeline is working, adding p6t gives you AI-generated translation drafts without leaving the terminal:

```bash
pnpm i18n:extract && p6t translate && pnpm i18n:compile
```

`p6t translate` reads `i18n.json` to find your source and target catalogs, translates only the strings that are missing or empty, and writes the results back. Existing translations are never overwritten.

See [Adding p6t to react-intl](#) for the full setup — including `p6t init`, `i18n.json` configuration, and the context files that guide translation quality.
