# @p6t/lingui

> This page documents p6t's intended design. The package is under active development; not all of this is implemented yet.

## What it provides

`@p6t/lingui` is the Lingui adapter for p6t. It wraps Lingui's `I18nProvider` internally, so Lingui's `<Trans>`, `useLingui()`, and macros work unchanged beneath it. It adds:

- `LocaleProvider` — Client Component boundary carrying locale + messages to the client tree, plus pre-configured Intl formatters via `useLocale()`
- Next.js middleware for public-page locale detection and URL-segment routing
- Server-side helpers (`initLocale`, `loadMessages`) so you don't need to copy boilerplate from bare Lingui examples
- If you need more control than the helpers provide, you can drop down to bare Lingui directly

## Root layout pattern

The structure mirrors bare Lingui. The Server Component layout owns `<html lang>` and server-side initialisation; `LocaleProvider` is the Client Component boundary:

```tsx
// app/[lang]/layout.tsx
import { allMessages, initLocale } from '@p6t/lingui/server'
import { LocaleProvider } from '@p6t/lingui'

export default async function RootLayout({ children, params }) {
  const { lang } = await params
  initLocale(lang)

  return (
    <html lang={lang}>
      <body>
        <LocaleProvider locale={lang} messages={allMessages[lang]}>
          {children}
        </LocaleProvider>
      </body>
    </html>
  )
}
```

`LocaleProvider` is locale-source-agnostic — it only cares about the value it receives, not where it came from. The same component works for every context below.

## Locale sources by page type

| Context | Locale source | URL shape |
|---|---|---|
| Public pages | Middleware → URL segment | `/en/about` |
| Private pages | User profile fetch (already happening for auth) | `/dashboard` |
| Sign-in / sign-up | Cookie (no auth fetch, no URL segment needed) | `/login` |

### Public pages (`app/[lang]/...`)

`@p6t/lingui` ships Next.js middleware that reads `Accept-Language` and matches against the locales in `i18n.json`.

Scope the middleware matcher to public routes only — exclude private routes entirely so they are never redirected.

### Private pages (`app/(private)/...`)

No `[lang]` segment, no middleware involvement. The private layout fetches the session server-side for auth anyway; the user's preferred locale comes along for free from that same fetch:

```tsx
// app/(private)/layout.tsx
export default async function PrivateLayout({ children }) {
  const user = await getSession()        // already needed for auth
  initLocale(user.locale)

  return (
    <LocaleProvider locale={user.locale} messages={allMessages[user.locale]}>
      {children}
    </LocaleProvider>
  )
}
```

### Sign-in / sign-up pages

The one genuine edge case: the user is unauthenticated (no profile fetch) and you don't want a locale in the URL. Use a locale cookie (`p6t-locale` or similar) set when the user previously changed their language preference, read server-side in the layout.

## `useLocale()` hook

Exposes the current locale string and pre-configured Intl formatters so components never need to instantiate `Intl.*` objects themselves:

```tsx
const { locale, formatDate, formatNumber, formatCurrency } = useLocale()
```

## generateStaticParams

For statically exported public pages, generate params from `i18n.json` the same way bare Lingui does:

```tsx
import { locales } from '@p6t/lingui'

export function generateStaticParams() {
  return locales.map((lang) => ({ lang }))
}
```
